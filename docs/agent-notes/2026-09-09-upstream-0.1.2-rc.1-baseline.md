# Upstream 0.1.2-rc.1 Baseline

The composed Harness baseline moves from `0.1.1-rc.2` to `0.1.2-rc.1`. Three decisions in that move are not mechanical and are recorded here.

## The deleted agent spine is flattened, not replaced by a bundle

`@deepseek-ai/dsh-agent-spine-demo` no longer exists upstream and was never published at `0.1.2-rc.1` (its last release is `0.1.2-alpha.2`), so the single `agent-spine` profile row had to go.

Upstream replaced that example package with a bundle layer: `@deepseek-ai/dsh-base` and `@deepseek-ai/dsh-acp-app` each ship a `cordis.patch.yml` that the official launcher discovers through a `dsh.bundle.patch` manifest field and applies over an empty profile root.

This deployment does not adopt that mechanism. `config/cordis.yml` stays one flat, fully explicit composition, and the spine's former children are now 25 ordinary rows in it. The reasons:

- The bundle patch layering is owned by the official launcher's profile boot. Depending on it would make the shipped composition a function of upstream patch files resolved at runtime, which is exactly the auditability this repository trades flatness for.
- A patch replaces a targeted row's whole `config` rather than merging into it. Layering would make every local override sensitive to upstream row identity, and `check:profile` could no longer compare a checked-in composition against a review manifest.
- `dsh-acp-app` composes the official automation-only `dsh-acp` transport and its command-line startup gate. Neither belongs in a deployment that composes its own ACP server.

The flattening preserves the exact set the bundle mounted for this profile's former config, including the ordering constraint that `agent-instructions` precede `tool-skill` because both prepend session-prefix messages in registration order. `toolBash: false` becomes the absence of the bundle's bash rows, leaving this profile's existing platform bash/pwsh switch authoritative.

Upstream's own base bundle stopped composing `dsh-invariants` and the `*/invariant` companions. This deployment keeps them: invariants are a runtime-diagnostics facility rather than an ACP capability, so removing a working facility is not part of following the protocol surface. `scripts/check-editor-profile.mjs` now resolves a subpath plugin specifier such as `@deepseek-ai/dsh-agent/invariant` to its owning runtime dependency.

## Two upstream contract changes were invisible to typecheck

`session.events` became `snapshotEvents()`, and `SessionSeq`/`SessionLogOffset` became branded numbers. Those surfaced as ordinary type errors.

Two did not, and both were only caught by running the suite:

- `permissionPresets.current()` changed from taking a detached event log to taking the `Session`, because permission state is now folded through `sessionProjections`. This repository declares its own structural read face for that optional service (`PermissionPresetDirectory`), so TypeScript never compared it against the real service and the mismatch reached runtime as `session.snapshotEvents is not a function`.
- `AgentLoop` added `sessionProjections` to its `inject` list. `tests/harness.ts` composed the testkit dependencies but not the projection registry, so the loop never published a factory and every session creation failed with `no agent factory registered`.

The structural read face remains the right shape for an optional capability, but it is a place where upstream drift is silent. Reading a projection during `session/new` also now materializes projection cells, which is why fixtures that synthesized a session log starting at seq 1 began failing contiguity validation and were corrected to start at seq 0.

`dsh-user-questions` replaced provider registration with a scope-filtered `user-questions/request` waterfall. The ACP answerer now declines to claim a request it does not own instead of rejecting it, because the service enforces the live/delegated caller boundary itself and reports `NO_PROVIDER` from its own terminal step. This drops the transport-owned `ASK_FOREIGN_AGENT` code.

## The compatibility gate is scoped and its divergence is recorded

`scripts/test-harness.mjs` previously copied `packages/acp/acp-interactive/tests` out of the checkout's working tree. That path has never existed at any tag inspected, so the gate had been reporting `fixture unavailable` rather than running, and it would have tested whatever ref a developer happened to have checked out.

The runner now extracts specs from the pinned ref in `config/upstream-baseline.json` via `git archive`, staged at real monorepo-relative paths so cross-package fixture imports resolve, with `vitest.harness.config.ts` redirecting the staged package's `../src` onto this repository's source.

Only `codec.spec.ts` runs verbatim. The measured reasons for the rest:

- Six specs (`approval`, `bridge`, `dispose`, `edges`, `multi-session`, `turns`) hang in the official `makeBridgeHarness()`. That harness composes none of `commands`, `skills`, or `sessionQuery`, all of which this server injects to serve slash commands, skills, and `session/load`, so its plugin fiber never activates. This was the apparent hang: 57 tests each burning a 30s timeout.
- Four specs (`content`, `mcp`, `model-control`, `updates`) import official private export names, two of them from modules the `0.1.2-rc.1` refactor introduced. The protocol behavior exists here under a different decomposition.

Neither class is a protocol gap. `0.1.2-rc.1` converged toward this server's design, and where the two still differ this one advertises more. Chasing a green upstream suite would mean renaming this repository's modules to mirror an upstream private structure and deleting ACP capabilities the official transport does not implement.

So the gate asserts the shared contract and makes everything else a reviewed statement. Every official spec must be classified; an unclassified or vanished spec fails as `fixture unavailable`, which is what forces the next upstream release through review instead of letting it pass silently.

Model configuration values stay this repository's opaque `provider:model` pair rather than upstream's JSON tuple. ACP treats the value as opaque, so the encoding is not a protocol difference and changing it would break nothing and fix nothing.
