# In-Process Subagents

Release `1.3.0` moves in-process subagents from the deferred list of the editor profile to a selected capability. The delegation semantics stay entirely with the published Harness packages; this repository adds only the attribution, projection, and lifecycle handling that turns one delegation into one editor tool card. Everything below was verified against source before it was built: the pinned Harness ref `dsh-v0.1.5-rc.1`, Zed's `acp_thread`, `agent_servers`, and native `spawn_agent` tool, and the community `claude-code-acp` adapter at its current `main`.

## What the references actually do

The commonly repeated description of subagent support — the parent emits a `Task` tool call, the adapter projects it as a tool card, a separate loop runs in the background, progress is streamed as `tool_call_update` content into the card, and the final answer returns as the tool result — is only partly what shipping implementations do.

`claude-code-acp` projects `Task`/`Agent` as a `think` card titled with the delegation description and carrying the prompt as content. For a client that has not declared its `subagent-transcript` `_meta` capability, it strips the child's text and thinking entirely and flattens the child's tool calls into the top-level transcript, stamping `_meta.claudeCode.parentToolUseId` on each so a capable client can re-nest them. Its nested transcript path depends on the ACP subagents RFD (agentclientprotocol/agent-client-protocol#1992), which is still open and absent from `@agentclientprotocol/sdk 1.4.0`. Its cancellation is the SDK's interrupt, and it holds a `session/prompt` open while background subagents it spawned are still live.

Zed's ACP client parses a `subagent_session_info` meta key on tool calls into `ToolCall.subagent_session_info` and treats `tool_call_update.content` as a replacement of the card's content list. The only producer of that key is Zed's own native `spawn_agent` tool, which presents the delegation as a `kind: other` card titled with the label and replaces the card content with the child's output when it finishes; no Zed UI path reads the key for an external ACP agent. Zed's client capabilities declare `terminal_output` and `terminal-auth` metas and nothing about child sessions.

DeepSeek Harness already owns the whole delegation lifecycle. `dsh-tool-subagent` exposes a `subagent` tool taking `description` and `prompt`; `dsh-subagent-spawn-in-process` and `dsh-subagent-fork-in-process` create the child through the same agent factory as the parent, with `parentSession`, `origin: 'subagent'`, and `delegationDepth` in the child header; the shared driver captures the parent's sandbox override and pins the child's approval policy to `never`, which `dsh-user-approval` answers with `rejected` before any listener runs; the child's final assistant output becomes the parent's tool result, and a non-completed run becomes an `isError` result carrying the stop reason, the provider diagnostic, and any partial text. A foreground run is cancelled through the tool's own `exec.signal`, and the parent loop's scheduler awaits every in-flight call before its turn settles, so the child is quiescent before the parent is. The seam publishes `subagent/start` and `subagent/end` with the delegating parent as the scoped carrier, and the parent session logs a durable `subagent/catalog` fact with the child id and label before the start edge.

## Decisions

Foreground only. Both delegation tool rows set `enableRunInBackground: false`. A child therefore lives strictly inside the parent's turn: `session/cancel`, `session/close`, and connection teardown all reach it through the parent's cancellation, and the bridge needs no second lifecycle, no held prompt, and no drain beyond the continuable drain it already performs. Parallel delegation is preserved because the tool declares itself concurrency-safe: a parent step may start several children at once. Background jobs, continuable children, `send_message`, `interrupt_agent`, `list_agents`, and the out-of-process ACP, Codex, and Claude Code backends stay deferred, and `config/editor-profile.json` records why.

No child interaction. Children inherit the parent's sandbox mode, carry approval `never`, and lose `ask_user_question` through the tool row's `toolFilter`. The bridge's `approval/request` and `user-questions/request` listeners already answer only for exact bridge-owned root agents, so even a child that reached them would be refused rather than prompting the editor from inside a card. Escalation stays with the parent, which can retry with the user's permission.

Attribution through the async context. Nothing in the seam carries the parent's tool call id: `subagent/start` names the child, and the child header names the parent session. Timing or the label would misattribute parallel delegations. The bridge instead wraps every `tools/execute` dispatch in an `AsyncLocalStorage` scope holding the calling agent and call id; the seam publishes `subagent/start` from within the same asynchronous chain as the tool body that called `ctx.subagents`, so the store is present in the listener and identifies the exact call. A start with no store, a child whose header does not name the origin agent, or an origin that is neither a bridge-owned root nor a tracked descendant is ignored.

One card, replaced content. Zed replaces card content on `tool_call_update`, so the bridge keeps a bounded per-card transcript and resends it whole: the child's tool calls with their tool-owned `presentCall` titles and settled markers, its committed assistant text, nested descendants indented under their own delegation entries, and the `subagent/end` stop reason. Reasoning is not projected, and neither is live child text: the durable `assistant/message` is the source, matching the rule that model-visible content is durable before it is shown. The parent's own `tool/result` settles the card through the ordinary tool-owned projection with the transcript kept ahead of the result, after which the card's links are dropped so no late child event can touch it. The card's title becomes the durable catalog label once the child is published, and `_meta.dsh_subagent` carries the child session id, provider, label, and final stop reason. Zed's `subagent_session_info` key is deliberately not emitted: no Zed path consumes it for an external agent, and a future consumer could try to open the child through this connection, which refuses child sessions.

Child sessions are not editor sessions. They share the parent's cwd, so `session/list` now omits any header with `origin: 'subagent'` or a `parentSession`, and `session/load` and `session/resume` refuse them, matching the official `dsh-acp` transport. A restored parent replays a delegation as its settled result card without the transcript; the child log remains on disk under its own id for inspection.

## Verification

`tests/subagents.spec.ts` composes the real `dsh-subagent`, spawn backend, and delegation tool over the in-memory harness and covers a delegation with a child tool call, parallel delegations attributed by a request-dependent scripted model, nested delegation rendering, `session/cancel` and bridge disposal while a child hangs, late-event suppression after settlement, list/load/resume exclusion, and the tracker's bounds and defensive branches. `tests/bin.spec.ts` drives the built launcher and the shipped `config/cordis.yml` under the `read-only` preset through one real delegation against a mock model server and asserts the card, its meta, the absence of permission requests, and the child's absence from `session/list`. The existing dispose, session, and MCP suites are unchanged and still pass.
